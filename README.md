# Помогатор2К (ai-challenge)

Чат-приложение для общения с [DeepSeek API](https://api-docs.deepseek.com/) и [OpenCode Zen](https://opencode.ai/docs/zen/) (подписка Go). Клиент — статическая HTML-страница (vanilla JS + CSS), сервер — **Python (FastAPI)**, который проксирует запросы к апстримам и не раскрывает API-ключи в браузере.

## Возможности

- Чат с выбранной моделью — DeepSeek или OpenCode (кастомный дропдаун с группами и ценовой маркировкой)
- Потоковый вывод ответов (SSE); текст ответа появляется целиком по завершении генерации (с вейтером на время раздумий/вывода); у reasoning-моделей рассуждения — под сворачиваемой меткой «Размышление»
- Счётчики токенов: общий «Сожжено токенов» (внизу блока параметров, включая саммаризационные запросы) + строка статистики в каждом блоке «вопрос+ответ» (время, вход/выход/рассужд. токены, стоимость)
- Настройки генерации: температура, top_p, top_k, стратегия контекста, лимит токенов, стоп-слова, JSON-режим
- **Стратегия контекста** (привязывается к чату первым сообщением): `Нет` (вся история), `Саммаризация` (история делится на чанки по N запросов; каждые 3 саммари сворачиваются в метасаммари), `Sliding Window` (в контекст уходят только последние N реплик), `Sticky Facts` (канонические факты + последние K реплик), `Branching` (ветвление чатов)
- **Sticky Facts**: факты извлекаются скрытым запросом после каждого ответа в виде пар «ключ — очень короткое значение» (`Имя: Иван`), хранятся в SQLite (переживают перезапуск) и показываются в панели справа от чата (перегородка тянется мышью); всегда подмешиваются в контекст — защита от галлюцинаций
- **Branching**: кнопка-иконка «Продолжить в другом чате» создаёт чат-снапшот (копия истории и настроек) в новой вкладке с иконкой ветки; исходный чат не меняется, ветвиться можно цепочкой
- **Память чата**: вкладка «Память» рядом с чатом — именованные хранилища пар «ключ — значение» (форма, строки с удалением); персистентные вкладки (иконка БД) сохраняются в БД и переживают перезапуск, неперсистентные живут до перезагрузки страницы; все пары из существующих вкладок подставляются в запросы к модели
- **Профиль пользователя**: кнопка-вид «Профиль» (с иконкой-человечком) справа в полосе видов — вкладки-профили, создаваемые полем названия и «+». Внутри профиля пять обязательных полей (как обращаться, стиль общения, язык диалога, формат ответа, ограничение ответа), кнопки «Сохранить» и «Установить текущим» (у активного профиля — зелёная галочка). Профиль не привязан к чату: активный общий для всех чатов и подставляется в системный промпт. Без активного профиля отправка в обычном чате блокируется сообщением «Необходимо создать и установить профиль.»
- **Задачи**: вид «Задачи» (между «Чат» и «Память») — чат со строгим протоколом этапов. LLM составляет план (шаг 2, ждёт подтверждения), затем после подтверждения выбирается режим: **выполнить всё сразу** или **по шагам с подтверждением каждого шага** (шаг 3), результат проверяет пользователь (шаг 4). На этапе шага «Доработать шаг» исправляет только текущий шаг с учётом замечаний (прогресс сохраняется); с финальной проверки доработка возвращает к плану. Каждый этап, план, шаги и результаты сохраняются в БД, поэтому задачу можно продолжить с любого этапа после перезагрузки или рестарта сервера. Завершённая задача показывает кнопку «Копировать ответ». Задачи живут во вкладках вида и удаляются вместе с ними (с подтверждением).
- **Сохранение вида**: выбранный вид (Чат/Задачи/Память/Профиль) и выбранная внутренняя вкладка восстанавливаются после перезагрузки страницы.
- **График токенов по сообщениям** (Chart.js, сворачиваемый): по умолчанию один столбик = всего токенов за сообщение; тумблер «цветной режим» раскладывает столбик на вход, выход, саммаризацию и факты с детализацией в тултипе; пунктир лимита контекста
- Команда `/optimize-prompt` с автокомплитом по «/» и модальным окном результата
- Серверные сессии-чаты: каждый чат — отдельный сервис с системным промптом, историей и метаданными
- Модель и настройки запоминаются per-чат: при переключении вкладок восстанавливаются модель и настройки чата; новый чат сбрасывает параметры к дефолту (`deepseek-v4-flash`)
- Первое сообщение нового чата становится его системным промптом и **привязывает модель и параметры** (temperature, top_p, top_k, стратегия контекста) к чату; лимит токенов, стоп-слова и режим ответа (Обычный/JSON) меняются на лету
- Внизу чата — инфоблок: модель, temperature, top_p, top_k, суммарные токены чата, максимальный контекст модели, индикатор использования контекста (`контекст: P%`, жёлтый ≥80%, красный ≥95%) и общая стоимость разговора в чате
- При достижении лимита контекста показывается понятное сообщение с кнопками «Новый чат» / «Подвести итоги» (чат не «застревает»)
- Идентификаторы чатов — случайные хеш-id (сквозная нумерация не раскрывается)
- **Персистентность**: сессии и история сохраняются в SQLite (`chats.db`) и полностью восстанавливаются после перезапуска сервера — диалог продолжается как будто сервер не выключался; восстанавливается и та вкладка, что была открыта
- TOON-сериализация структурированных данных в промптах (контекст «Итогов», метаданные)
- Консольное логирование клиента: в DevTools видно, что браузер отправляет и получает
- API-ключи хранятся только на сервере

## Требования

- Python **3.10+** (разработано и проверено на 3.14)

## Установка

```bash
git clone https://github.com/vitchuk/ai-challenge.git
cd ai-challenge
```

Создайте файл `.env` на основе примера и укажите API-ключи:

```bash
copy .env.example .env
```

Откройте `.env` и вставьте ключи (достаточно хотя бы одного):

```
DEEPSEEK_API_KEY=sk-xxxxxxxxxxxxxxxx
OPENCODE_API_KEY=zen-xxxxxxxxxxxxxxxx
PORT=3000
CHATS_DB_PATH=chats.db
```

`OPENCODE_API_KEY` — ключ OpenCode Zen (подписка Go), берётся на <https://opencode.ai/auth/zen>. `CHATS_DB_PATH` — путь к файлу SQLite с сессиями/историей (по умолчанию `chats.db`).

## Запуск

```cmd
start-server.cmd
```

Скрипт создаст виртуальное окружение `.venv` (при первом запуске), установит зависимости и запустит сервер. Или вручную:

```bash
py -3.14 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python -m server.main
```

Откройте в браузере: <http://localhost:3000> (порт из `.env`).

## Тесты

```bash
.venv\Scripts\python -m pip install -r requirements-dev.txt
.venv\Scripts\python -m pytest
```

## Как это работает

1. Клиент создаёт серверную сессию (`POST /api/sessions`) — каждый чат-вкладка соответствует одной сессии; id сессии — случайный хеш (нумерация не раскрывается).
2. Отправка сообщения — `POST /api/sessions/{id}/messages`; сервер дописывает сообщение в историю сессии, вызывает апстрим и стримит нормализованные SSE-события (`session`/`reasoning_start`/`reasoning_end`/`request_log`/`done`/`facts`+метаданные). Текст ответа не стримится пофрагментно — он приходит целиком в `done.content`, а на время генерации клиент показывает вейтер. Первое сообщение нового чата становится его **системным промптом** (первый запрос уходит как `[system]`) и **привязывает модель и параметры** (`temperature`, `top_p`, `top_k`, `context_strategy`); лимит токенов, стоп-слова и режим ответа остаются гибкими. Стратегия контекста определяет сборку запроса: чанковая саммаризация, скользящее окно, факты или ветвление. Для обычных чатов обязателен активный **профиль пользователя**: его данные добавляются ведущим системным сообщением, а без профиля отправка отклоняется (`400 profile_required`). **Задачи** (вид «Задачи») — отдельные сессии со строгим протоколом: план → подтверждение → выполнение → проверка; состояние хранится в `session_task_state`, поэтому продолжение возможно с любого этапа.
3. История и метаданные (время, токены, стоимость), а также записи о запросах к LLM (для графика/счётчика), состояние саммаризации и факты живут на сервере и сохраняются в SQLite (`chats.db`). Закрытие вкладки / модалки удаляет сессию (`DELETE`) — и из памяти, и из БД.
4. **Персистентность и восстановление**: при перезапуске сервера все чаты и их история загружаются из БД; клиент при загрузке страницы запрашивает `GET /api/sessions` и восстанавливает все вкладки — диалог продолжается с полным контекстом. Модель и настройки каждого чата запоминаются (`session.model`/`session.settings`), а открытая вкладка — через `POST /api/sessions/{id}/activate`, поэтому после рестарта активируется именно тот чат, что был открыт. Изолированные сессии `/optimize-prompt` в БД не сохраняются.
5. TOON используется для вложения структурированных данных (метаданные, контекст «Подвести итоги») в текст промптов — это экономит токены по сравнению с JSON. HTTP-оболочка к апстримам остаётся JSON (их API принимает только JSON).
6. Для моделей DeepSeek первым системным сообщением добавляется промпт идентичности («Ты — DeepSeek…»): модели DeepSeek V4 ошибочно представляются «ассистентом OpenAI», промпт фиксирует корректную идентичность.

## Команда /optimize-prompt

При вводе «/» в поле чата появляется список команд. `Tab`/`Enter`/клик вставляет `/optimize-prompt ` в начало строки. После команды введите запрос, например:

```
/optimize-prompt Напиши краткое приветствие для блога о Python
```

Создаётся временный изолированный чат (модель — выбранная в текущем чате; `temperature 0.1`, `top_p 0.01`) с промптом-инженером. Результат показывается в модальном окне с кнопками «Копировать» и «Закрыть» (закрытие также по клику вне окна / `Esc`). При закрытии временная сессия удаляется и с сервера, и из клиента.

## Консольное логирование

В DevTools (`F12` → Console) браузер пишет, что он отправляет на сервер и получает от него:

- `[клиент→сервер] …` — исходящие запросы (POST/DELETE и их тела);
- `[клиент←сервер] …` — входящие события (SSE-чанки, статусы).

Логирование включается флагом `CLIENT_LOG_ENABLED` в начале `public/app.js`.
