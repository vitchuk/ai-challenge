# Спецификация ai-challenge

Документ описывает текущее состояние проекта. Обновляется при каждом коммите (см. раздел [История изменений](#10-история-изменений)).

## 1. Обзор

Чат-приложение для общения с [DeepSeek API](https://api-docs.deepseek.com/) и [OpenCode](https://opencode.ai/) (подписка Go + бесплатные Zen-модели).

| Параметр | Значение |
|---|---|
| Название | Помогатор2К |
| Назначение | Веб-чат с LLM с потоковым выводом, мультичатами, командами |
| Клиент | Статическая HTML-страница (vanilla JS + CSS); график контекста — Chart.js 4.x (CDN) |
| Сервер | Python 3.10+, FastAPI + uvicorn, httpx |
| Формат ответов | SSE (Server-Sent Events); текст ответа приходит целиком в финальном событии `done`, пофрагментная стриминг-выдача клиенту не используется |
| Сериализация структ. данных в промптах | TOON (Token-Oriented Object Notation) |
| Язык интерфейса | Русский |

## 2. Архитектура

```
Браузер ──HTTP/JSON + SSE──> API-слой (FastAPI) ──> Сервисный слой ──> Провайдеры ──JSON/SSE──> DeepSeek / OpenCode
                             тонкие маршруты,        ChatService,       роутинг по model,
                             валидация, статика      SessionRegistry    white-list'ы, ключи
```

- Браузер общается только с локальным сервером; API-ключи в клиент не попадают.
- Сервер хранит сессии-чаты (персистентно — в SQLite) и проксирует запросы в апстрим, пересылая клиенту **нормализованные** SSE-события (а не сквозные чанки апстрима).
- Апстрим выбирается по модели: `opencode/…` → OpenCode, иначе → DeepSeek.
- Сессии и история сохраняются в файл SQLite (`chats.db`, настраивается `CHATS_DB_PATH`) и при перезапуске сервера полностью восстанавливаются.

### 2.1. Мультиагентная архитектура (задел)

`ChatService` уже выступает как «агент»: роль (системный промпт) + свои настройки генерации (temperature, top_p, **top_k**, max_tokens, stop) + модель + история с метаданными; он не зависит от HTTP и UI. В будущем планируется оркестратор (агент-модератор), который будет передавать контроль субагентам по очереди, вкладывая друг другу состояние через TOON-контекст (`ChatService.to_toon_context()`). В текущей итерации оркестратор не реализован — заложен только фундамент (независимые сервисы-агенты + реестр + TOON-контекст), поэтому следующий слой не потребует редизайна.

## 3. Сервер (`server/`)

### 3.1. Приложение и запуск

- `server/main.py:create_app()` собирает FastAPI-приложение: маршруты сессий и моделей + раздача статики из `public/` (StaticFiles, html=True).
- Lifespan приложения создаёт общий `httpx.AsyncClient` (таймаут 600 с, connect 15 с — большие запросы/долгая генерация не упираются в дефолтные 5 с), реестр сессий `SessionRegistry` с SQLite-хранилищем (`build_registry`) и восстанавливает чаты.
- `Cache-Control: no-cache` для HTML/JS/CSS (middleware) — браузер всегда ревалидирует статику.
- Запуск: `python -m server.main` (читает `PORT` из `.env`/окружения) или `uvicorn server.main:app`.
- Автодокументация HTTP API: `/docs` (OpenAPI).

### 3.2. `POST /api/sessions` — создать сессию

**Запрос:**

```json
{ "model": "opencode/glm-5.3", "settings": {"temperature": 0.1, "top_p": 0.01}, "system_prompt": "…", "kind": "chat" }
```

- `model` — необязательная модель по умолчанию (может переопределяться на запрос).
- `settings` — необязательные параметры генерации (валидируются, см. §3.5).
- `system_prompt` — необязательный системный промпт.
- `kind` — тип сессии: `chat` (по умолчанию), `summary` (чат «Итоги», контекст строится сервером), `ephemeral` (изолированный чат команды `/optimize-prompt`).

**Ответ:** `201`, `{"id": "…", "model": …}`. Идентификатор сессии — **случайный 16-hex токен** (`secrets.token_hex(8)`), не раскрывающий сквозную нумерацию чатов.

### 3.3. `POST /api/sessions/{id}/messages` — отправить сообщение (SSE)

**Запрос:**

```json
{ "content": "текст", "model": "…", "settings": {…}, "system_prompt": "…" }
```

- `content` — текст сообщения (обязателен). Сервер дописывает его в историю сессии.
- `settings` — параметры генерации **инкапсулируются за чатом** (`session.settings`, персистятся). Параметры делятся на **привязываемые** и **гибкие**:
  - привязываемые (фиксируются **первым сообщением** чата, далее игнорируются): `temperature`, `top_p`, `top_k`, `context_strategy`;
  - гибкие (меняются на лету, на каждый запрос): `max_tokens`, `stop`, `response_format`.
  При запросе без `settings` используются настройки сессии.
- `system_prompt` — необязательный дополнительный системный промпт, вставляемый перед остальными (используется JSON-режимом клиента).

Переданная `model` **привязывается к чату первым сообщением** (`session.model`); изменения модели для привязанного чата игнорируются. При успешном завершении стрима строка сессии (модель + настройки) персистится в БД.

**Первое сообщение обычного чата (`kind=chat`) = системный промпт.** Если история пуста и `system_prompt` не задан, первое сообщение становится системным промптом сессии (`seed_system_message`): записывается в историю с ролью `system`, `session.system_prompt` заполняется. Первый запрос уходит в апстрим как `[system]`; второй+ — `[system: первое, assistant, user: второе, …]` (без дубля первого сообщения). При ошибке первого запроса сид откатывается (повторная попытка снова станет системным промптом). Чат «Итоги» (динамический TOON-промпт) и `ephemeral`-сессии не затрагиваются.

**Ответ (успех):** `200`, `text/event-stream`. Сервер стримит нормализованные события:

```
data: {"type":"session","id":"<хеш-id>"}               # идентификатор сессии
data: {"type":"reasoning_start"}                       # начало раздумий (вейтер)
data: {"type":"reasoning_end","content":"…"}           # конец раздумий: полный текст
data: {"type":"request_log","record":{…}}              # учёт запроса к LLM (график/счётчик)
data: {"type":"done","content":"…","meta":{…}}         # завершение: весь текст + метаданные
data: {"type":"facts","items":[…] }                    # стратегия facts: обновлённый список фактов
data: {"type":"error","error":"…"}                     # ошибка (user-сообщение откатывается)
data: {"type":"error","error":"…","code":"context_length_exceeded"}  # лимит контекста
```

Событие `request_log` отправляется на каждый запрос к LLM (основной ответ, скрытая саммаризация или извлечение фактов): `record` = `{index, kind, prompt_tokens, completion_tokens, reasoning_tokens}`, где `kind` — `main`, `summary` или `facts`, `index` — порядковый номер запроса в чате, `reasoning_tokens` — рассуждения (часть `completion_tokens`). Записи уже отданных запросов повторно не отправляются. Событие `facts` приходит после `done` при стратегии `facts` (панель фактов клиента).

При ошибке **лимита контекстного окна** апстрима сервер распознаёт её (парсер `_classify_upstream_error` в `providers/engine.py` по текстам `maximum context length is N`, `context length (N)`, `requested about N`, `longer than the model's context`, 400) и отдаёт локализованное сообщение + машинный `code: "context_length_exceeded"` (в `error` — русский текст с числами: макс. и запрошено). Клиент по этому коду показывает спец-блок (см. §5.3). Прочие ошибки — без `code`.

Текст ответа **не стримится пофрагментно** — `delta`-события клиенту не отправляются. Пока модель генерирует ответ (и раздумывает), клиент показывает **вейтер** (спиннер); весь текст приходит целиком в `content` финального события `done`.

Рассуждения (reasoning) передаются **двумя событиями**: `reasoning_start` — момент начала раздумий (клиент показывает спиннер на метке «Размышление»), и `reasoning_end` — завершение раздумий с **полным** накопленным текстом (`content`). После `reasoning_end` вейтер остаётся до `done` — ответ появляется сразу целиком.

`meta` содержит: `model` (клиентский id модели, напр. `opencode/glm-5.3`), `time_s`, `prompt_tokens`, `completion_tokens`, `reasoning_tokens`, `cost_usd`, `finish_reason`, а также `summarized` (`true`, если основной запрос собран с саммари контекста; иначе отсутствует). Счётчики токенов берутся из `meta` (отдельного `usage`-события клиенту не шлётся).

**Ошибки (JSON `{"error": "…"}`):**

| Код | Причина |
|---|---|
| 404 | Сессия не найдена |
| 409 | Сессия занята (в этом чате уже идёт запрос) |
| 400 | `opencode/…`-модель не поддержана |
| 400 | Обычный чат без активного профиля (`code: "profile_required"`) |
| 422 | Некорректное тело (например, пустой `content`) |
| 500 | Не задан нужный API-ключ |
| 401/402/429/… | Код и сообщение ошибки апстрима (проксируется) |

### 3.4. `GET /api/sessions`, `GET /api/sessions/{id}`, `POST /api/sessions/{id}/activate`, `DELETE /api/sessions/{id}`

- `GET /api/sessions` — список всех сессий с историей для восстановления клиента: `{"data": [...], "active_id": "…"|null}` (в порядке создания; ephemeral-сессии исключены). Каждая сессия: `{id, kind, model, system_prompt, settings, last_active, history, requests, facts, memory, title, parent_id}`. `active_id` — сессия, открытая у пользователя (для восстановления активной вкладки).
- `GET /api/sessions/{id}` — полное состояние сессии: `{id, kind, model, system_prompt, settings, last_active, history: [{role, content, meta}], requests: [{index, kind, prompt_tokens, completion_tokens, reasoning_tokens}], facts: [str], memory: [{id, name, persistent, items: [[ключ, значение]]}], title, parent_id}`. Роль `system` в начале истории — первое сообщение (системный промпт). `requests` — учёт всех запросов к LLM (для графика токенов по сообщениям и счётчика). `facts` — канонические факты (стратегия `facts`); `memory` — вкладки памяти чата (§3.10); `title`/`parent_id` — название вкладки и родитель (для ответвлённых чатов).
- `PUT /api/sessions/{id}/memory` — синхронизирует **память чата** (§3.10): тело `{"stores": [{id?, name, persistent, items: [[ключ, значение], …]}, …]}`. Сервер валидирует (непустые строки; лимиты длин/количеств, невалидное молча отбрасывается), заменяет состояние и сохраняет в БД **только персистентные** вкладки. Ответ `{"memory": [...]}`. Ошибки: `404` (сессии нет), `400` (не `kind=chat`).
- `POST /api/sessions/{id}/branch` — создаёт **чат-снапшот (ветку)** от обычного чата. Тело — `{"title": "…"}` (необязательно). Копируются история (включая сид), `system_prompt`, `model`, настройки (стратегия наследуется и уже «привязана»), состояние чанковой саммаризации, факты и память; журнал `llm_requests` **не** копируется (график нового чата с нуля, «Сожжено токенов» не меняется). `parent_id` — без FK: удаление родителя не затрагивает потомка. Ответ `201 {"id", "model"}`. Ошибки: `404` (сессии нет), `400` (не `kind=chat`).
- `POST /api/sessions/{id}/activate` — отмечает сессию как активную (клиент вызывает при переключении вкладок; хранится в БД). `204` при успехе, `404` если сессии нет.
- `DELETE /api/sessions/{id}` — удаляет сессию из памяти сервера и хранилища (если удалялась активная — маркер активности очищается). `204` при успехе, `404` если сессии нет.

### 3.5. `GET /api/models` — список моделей с ценами

Агрегирует модели всех настроенных провайдеров и возвращает `{"object":"list","data":[{"id","owned_by","price","context"}]}`, где `price` — цена за 1M выходных токенов (для маркировки в UI; `0` — бесплатные, `null` — вне карты цен), `context` — максимальный размер контекста в токенах из `MODEL_CONTEXT` (`null` — лимит не раскрыт апстримом). Значения `MODEL_CONTEXT` подтверждены probe-запросами (валидация `prompt+max_tokens` до генерации): DeepSeek (все) — 1048576; `kimi-k2.6`/`hy3`/`ling-3.0-flash-fin-free` — 262144; `longcat-2.0` — 1048580; `hy4-preview`/`opencode/deepseek-*` — 1048576; `nemotron-*-free` — 1000000. Для GLM/Kimi-k3/MiMo/Omen и части free-моделей лимит апстримом не раскрывается — `context: null` (в UI «—»).

- DeepSeek (если задан `DEEPSEEK_API_KEY`): все модели из `GET https://api.deepseek.com/models`, `owned_by: "deepseek"`.
- OpenCode Go (если задан `OPENCODE_API_KEY`): модели из `/zen/go/v1/models`, отфильтрованные по `GO_CHAT_MODELS`.
- OpenCode Zen — бесплатные: модели из `/zen/v1/models`, отфильтрованные по `ZEN_FREE_MODELS`.

Все OpenCode-модели — с префиксом `opencode/`, `owned_by: "opencode"`.

Ошибки: `500` (не задан ни один ключ), `502` (не удалось получить модели ни из одного апстрима). Отказ одного апстрима не роняет весь список.

### 3.6. Валидация параметров генерации (`GenerationSettings`)

Перенесено из прежней Node-версии; невалидные значения молча игнорируются. Параметры делятся на **привязываемые** первым сообщением (`temperature`, `top_p`, `top_k`, `context_summary`) и **гибкие** (`max_tokens`, `stop`, `response_format`):

- `temperature` — число 0–2.
- `top_p` — число 0–1; `0` нормализуется в `0.01` (диапазон DeepSeek — `(0, 1.0]`).
- `top_k` — положительное целое. **Хранится** в настройках для будущих провайдеров, но в DeepSeek/OpenCode **не передаётся** (их API его не поддерживают).
- `context_strategy` — `{"strategy": "none"|"summarize"|"sliding"|"facts"|"branching", "n": int, "k": int}` — стратегия управления контекстом (§3.9). Невалидная стратегия → `none`; `n`/`k` не-число → дефолт (`n=5` для summarize, `n=10` для sliding, `k=10`), вне диапазона `1–20` — клэмпится. В апстрим не передаётся (серверная механика). **Миграция легаси** `context_summary {enabled, requests_per_summary|keep_recent}`: `enabled=true` → `{strategy:"summarize", n:…}`, иначе `{strategy:"none"}`; при наличии обоих ключей приоритет у `context_strategy`.
- `max_tokens` — положительное целое.
- `stop` — массив непустых строк, до 16 элементов.
- `response_format` — `{"type":"json_object"}`.

### 3.7. Реестр сессий (`SessionRegistry`)

- `create/get/delete/list` — управление живыми сессиями; идентификаторы — **случайные 16-hex токены** (без сквозной нумерации; `secrets.token_hex(8)` с проверкой уникальности).
- `build_summary_context(exclude_id)` — собирает содержимое всех остальных сессий (история + метаданные) и сериализует его в **TOON**.
- Чат «Итоги» (`kind=summary`): при каждом запросе системный промпт пересобирается — `SUMMARY_CONTEXT_PROMPT` + TOON-контекст всех остальных сессий (follow-up вопросы работают).
- `remember_pair(chat)` — атомарно персистит последнюю пару (user|system + assistant) после успешного стрима + обновляет модель и настройки сессии (upsert).
- `persist_new_requests(chat)` / `persist_summary_state(chat)` / `persist_facts(chat)` — сохраняют записи о запросах, состояние чанковой саммаризации (курсор + саммари) и факты (ephemeral пропускаются).
- `branch(chat, title)` — создаёт чат-снапшот (ветку): копирует историю, системный промпт, модель, настройки, состояние саммаризации и факты; журнал запросов не копирует.
- `set_active/get_active` — маркер активной (открытой) сессии; `get_active` валидирует существование; удаление активной очищает маркер.
- `restore()` — загружает все сессии из SQLite при старте (включая маркер активности).
- TTL-очистка осиротевших сессий **убрана**: сессии персистентны и удаляются только по `DELETE` (закрытие вкладки/модалки).

### 3.8. Хранилище (`SessionStore`, SQLite)

- Сессии и история сохраняются в файл SQLite (`CHATS_DB_PATH`, по умолчанию `chats.db`; `:memory:` — для тестов). stdlib `sqlite3`, `WAL`, `foreign_keys=ON`.
- Таблицы: `sessions` (id, kind, model, system_prompt, settings/JSON, created_at, last_active, **parent_id**, **title**), `messages` (session_id FK ON DELETE CASCADE, role, content, meta/JSON, created_at), `llm_requests` (session_id FK ON DELETE CASCADE, idx, kind, prompt_tokens, completion_tokens, reasoning_tokens, created_at — для графика/счётчика), `session_summary_state` (session_id PK FK ON DELETE CASCADE, chunks, items/JSON, updated_at — курсор и накопленные саммари), `session_facts` (session_id PK FK ON DELETE CASCADE, items/JSON, updated_at — канонические факты), `session_memory` (session_id PK FK ON DELETE CASCADE, stores/JSON, updated_at — персистентные вкладки памяти), `profiles` (id, name, fields/JSON, updated_at — профили пользователя) и `app_state` (key/value — маркер активной сессии и активного профиля).
- **Миграция схемы**: при открытии ранее созданной БД недостающие колонки (список `MIGRATIONS`, напр. `parent_id`/`title` в `sessions`) досоздаются через `ALTER TABLE ADD COLUMN`, а устаревшие таблицы (список `DROPS`) удаляются — обновление версии не требует пересоздания БД и не теряет историю.
- Сессия сохраняется при создании (upsert); сообщения — **атомарной парой user+assistant** по завершении стрима. Краш/ошибка/откат → пара не пишется (консистентно с rollback).
- **Изолированные (ephemeral) сессии `/optimize-prompt` в БД не сохраняются** — они временные.
- При перезапуске сервера `build_registry()` создаёт хранилище и полностью восстанавливает все чаты с историей, записями о запросах (`requests`) и состоянием саммаризации — контекст диалога, график и сжатие сохраняются.

### 3.9. Стратегии управления контекстом

Привязываемая настройка `context_strategy` (фиксируется первым сообщением, как `temperature`) выбирает способ сборки контекста **для обычных чатов** (`kind=chat`; у «Итогов» и ephemeral стратегия игнорируется — уходит вся история). Варианты: `none`, `summarize`, `sliding`, `facts`, `branching`.

#### 3.9.1. Summarize — чанковая саммаризация

`n` — сколько запросов покрывает одно саммари.

- **Единица чанкования — «запрос».** Запрос №1 — первое сообщение чата (системный сид): в саммаризацию входит только **ответ** на него (текст сида и так остаётся системным промптом и не дублируется); каждый следующий запрос — пара «вопрос+ответ». Висящее сообщение (ответ ещё не получен) в подсчёт не входит.
- Перед основным запросом каждый ещё не сжатый завершённый чанк сжимается **скрытым запросом** к той же модели (системный промпт `SUMMARIZER_SYSTEM_PROMPT`). Курсор «сколько чанков сжато» хранится в сессии — повторно готовые чанки не пересчитываются (сам является кэшем).
- Когда накопилось **3 саммари** (`COLLAPSE_SUMMARIES_AT`), они сворачиваются в одно **метасаммари** (скрытый запрос, на входе — тексты саммари), и список начинается заново — цикл повторяется.
- Основной запрос: `[системный промпт/сид] + [служебное сообщение со всеми саммари] + [сообщения после курсора без изменений]`. Рамка — `[Саммари начала диалога]`, секции `Саммари k:`.
- Пример (n=3): запросы 1–3 копятся; на **4-м** создаётся саммари№1 — в модель идут `[системный] + S1 + запрос4`; на **7-м** — S2: `[системный] + S1 + S2 + запрос7`; на **10-м** — S3 и сворачивание S1+S2+S3 в метасаммари M: `[системный] + M + запрос10`; далее цикл.
- **Деградация**: сбой сжатия чанка — курсор не двигается, этот и следующие чанки идут без изменений; сбой свёртки — саммари остаются и будут свёрнуты следующим ходом.

#### 3.9.2. Sliding Window — скользящее окно

- **Единица окна — обмен** «реплика пользователя + ответ ассистента»; **обмен №1 — системный сид и ответ на него** (сид равноправен остальным и в окне уходит с ролью `system`, как хранится).
- Основной запрос: `[последние n обменов] + [новое (висящее) сообщение]`. Новое сообщение в окно не входит.
- Если обменов не больше `n` — уходит **вся история** целиком (с сидом). Выпавшие из окна сообщения (в т.ч. сид) **не отправляются вовсе** — принудительного system-сообщения нет; если system-записи в окне нет, запрос уходит без неё (провайдерский `DEEPSEEK_IDENTITY_PROMPT` добавляется отдельно на уровне провайдера).
- Всё старше окна **в API не отправляется**, но остаётся в UI-истории и БД.
- Дополнительных обращений к модели нет; экономия видна по `prompt_tokens`/графику.

#### 3.9.3. Sticky Facts — канонические факты

`k` — размер окна обменов (то же правило, что в `sliding`: сид не привилегирован).

- Контекст основного запроса: `[служебное сообщение «[Установленные факты]»: нумерованные строки «ключ: значение» + указание опираться и не выдумывать]` + окно `[последние k обменов] + [новое сообщение]`. Блок фактов присутствует **всегда** и ставится после ведущего system-сообщения (если оно есть в окне), иначе первым.
- **Формат фактов** — пары **«ключ — очень короткое значение»** (`[["Имя","Иван"], ["Город","Москва"], …]`); ключ — категория одним словом, значение — 1–3 слова без связок (не «Пользователя зовут Иван», а `Имя: Иван`).
- **Экстракция**: после **каждого успешного** `done` основного ответа — скрытый запрос к той же модели (параметры чата, кроме `response_format`) с системным промптом `FACTS_SYSTEM_PROMPT`; на входе — текущий список фактов (пары) и **новое сообщение пользователя**. Модель возвращает полный обновлённый JSON-объект `{"ключ": "значение"}`. `_parse_facts` терпим к Markdown-оградам и принимает также массив объектов `{"key","value"}` и массив пар; результат нормализуется (дедуп по ключу: позиция первого, значение последнего). При сбое парсинга/запроса старый список сохраняется (деградация), чат не прерывается.
- **Легаси**: факты старого формата (массив строк) при загрузке рендерятся как есть; со следующей экстракцией список полностью перезаписывается парами (старого списка передаётся модели текстом).
- Результат сохраняется в сессии (таблица `session_facts`), переживает рестарт; отдаётся в состоянии сессии и по SSE-событию `{"type":"facts","items":[…]}` после `done`.
- Токены экстракции — запись `llm_requests` с `kind="facts"`; на графике отдельный сегмент «факты».

#### 3.9.4. Branching — ветки диалога

- Сборка контекста **не меняется** (вся история, как `none`) и **никаких ограничений на число запросов/сообщений/ветвлений нет**; параметры `n`/`k` для `branching` не используются ни сервером, ни клиентом (инпут параметра для этой стратегии скрыт).
- `POST /api/sessions/{id}/branch` (§3.4): кнопка-иконка «Продолжить в другом чате» создаёт чат-снапшот.
- Ветвиться можно многократно (цепочки); удаление родителя не ломает потомка.

#### 3.9.5. Общее

- Все стратегии — привязываемые; стратегия `summarize`/`sliding`/`facts` шлёт скрытые запросы с параметрами чата, **кроме `response_format`** (JSON-режим относится к ответу пользователю). Саммари и факты — служебные данные, в видимую историю и `history` не попадают.
- Токены всех скрытых запросов учитываются в «Сожжено токенов» и на графике (типы `summary`/`facts`).

### 3.10. Память чата (memory)

Независимая от стратегии функциональность: у обычного чата (`kind=chat`) есть **вкладки памяти** — именованные хранилища пар «ключ — значение».

- Вкладка: `{id, name, persistent, items: [[ключ, значение], …]}`. **Персистентность задаётся при создании** вкладки (флаг `persistent`; после создания вкладки кнопка БД сбрасывается): персистентные сохраняются в БД, неперсистентные живут только до перезагрузки страницы. При восстановлении после перезагрузки клиент **пересинхронизирует** память чата (`PUT`), поэтому устаревшие неперсистентные вкладки уходят и с сервера — они пропадают из контекста запросов к LLM (в UI их тоже нет).
- API: `PUT /api/sessions/{id}/memory` (§3.4) — полный синк состояния (клиент присылает все вкладки); сервер заменяет состояние и персистит только персистентные. `GET` отдаёт `memory`.
- **Подстановка в LLM**: если у чата есть непустые вкладки, в основной запрос (любая стратегия) добавляется служебное user-сообщение `[Память чата]` — секции `## {название}` со строками `ключ: значение` из **всех** вкладок и указание использовать данные **только когда запрос пользователя напрямую их касается** (не пересказывать память в каждом ответе и не упоминать её наличие); вставляется сразу после system-сообщения (или первым, если system нет). Пустая память — блок не добавляется. Скрытые запросы (саммаризация/факты) память не получают.
- **Хранилище**: таблица `session_memory (session_id PK FK ON DELETE CASCADE, stores JSON, updated_at)` — только персистентные вкладки; при рестарте сервера они восстанавливаются.
- **Ветвление** наследует память (как факты/саммари).

### 3.11. Профиль пользователя (profiles)

Глобальная сущность, **не привязанная к чату**: активный профиль один на всё приложение и подставляется в системный промпт **обычных чатов** (`kind=chat`).

- **Профиль**: `{id, name, fields: {address, style, language, format, limit}}` — название и пять обязательных полей: «Как ко мне обращаться», «Стиль общения», «Язык диалога», «Формат ответа», «Ограничение ответа». Неполные профили (без названия или любого поля) при синхронизации молча отбрасываются.
- **API**: `GET /api/profiles` → `{"profiles": [{id, name, fields}], "active_id": "…"|null}`; `PUT /api/profiles` — полный синк состояния (`{"profiles": [...], "active_id": …}`), как у памяти чата. Активный профиль валидируется по сохранённым (если его нет — снимается).
- **Хранилище**: таблица `profiles` (определения) + ключ `app_state["active_profile"]` (активный); переживает рестарт сервера.
- **Подстановка в LLM**: при наличии активного профиля в основной запрос обычного чата добавляется ведущее system-сообщение — вступление `PROFILE_SYSTEM_PREFIX` («Ты полезный ассистент, который следует профилю пользователя во всех ответах. Базовые правила безопасности и фактической точности имеют приоритет над профилем. Не сообщай, что ты используешь профиль…») и блок `[Профиль пользователя]` со строками `Подпись: значение`. Вставляется первым сообщением (через `extra_system`), поэтому присутствует при любой стратегии контекста. Скрытые запросы (саммаризация/факты) профиль не получают.
- **Блокировка без профиля**: если активного профиля нет, `POST /api/sessions/{id}/messages` для `kind=chat` возвращает `400` `{"error": "Необходимо создать и установить профиль.", "code": "profile_required"}`; сообщение в историю не пишется. Чаты «Итоги» и ephemeral-сессии (`/optimize-prompt`) не затрагиваются.

## 5. Клиент (`public/`)

### 5.1. Компоненты

Дополнительно: кнопка «Продолжить в другом чате» (стратегия `branching`) рядом с полем ввода, дропдаун команд над полем ввода, модальное окно `/optimize-prompt`. Подключается `Chart.js 4.x` (CDN).
- `style.css` — тёмная тема; стили сообщений, вкладок, дропдауна моделей, дропдауна команд, модального окна, графика, радиокнопок стратегии, панели фактов, ветвления, памяти чата и профиля; тонкие скроллбары (`.tabs`, `.settings`, `.chat__facts`, `.memory__tabs`, `.memory__editor`, область сообщений) в палитре темы; глобальное правило `[hidden] { display: none !important; }` (скрытие не перебивается собственным `display` элемента).
- `app.js` — логика: серверные сессии-чаты, стрим SSE, команды, модалка, консольное логирование, счётчик токенов, график, стратегии контекста (панель фактов, ветвление), профили пользователя (вид «Профиль», блокировка отправки без активного профиля).

### 5.2. Серверные сессии и восстановление

- Каждая чат-вкладка соответствует серверной сессии: при создании вкладки вызывается `POST /api/sessions`, `chat.sid` сохраняется в состоянии чата.
- Отправка сообщения — `POST /api/sessions/{sid}/messages` с `{content, model, settings, system_prompt}`; ответ парсится как нормализованные SSE-события.
- Закрытие вкладки (крестик «×», после `confirm`) вызывает `DELETE /api/sessions/{sid}` — серверная история удаляется из памяти и БД.
- Чат «Подвести итоги» (`kind=summary`) создаётся по кнопке; контекст собирается сервером в TOON.
- **Восстановление при загрузке страницы**: клиент делает `GET /api/sessions`; если список непуст, все чаты восстанавливаются как вкладки (история — блоками `.qa` со статистикой из `meta`; заголовок — сохранённый `session.title` (для ответвлённых) или по первому вопросу / «Подвести итоги» для summary; у чатов с `parent_id` — иконка ветки; пустой чат — «Новый чат» с приветствием; модель вкладки — из `session.model`; записи о запросах — из `session.requests`, из них же считается «Сожжено токенов» и строится график; факты — из `session.facts`). Активируется **та вкладка, что была открыта у пользователя** (`active_id` из ответа); если её нет — чат с максимальным `last_active`. Если список пуст — создаётся новый чат.
- Ограничение восстановления: текст рассуждений и JSON-конверты не являются частью истории — восстановленные ответы показываются как текст + статистика. Контекст для модели (история и метаданные) сохраняется полностью.

### 5.3. Поведение

- Выбор модели: кастомный дропдаун `.dropdown`; панель заполняется из `GET /api/models` (с ценами), группировка по `owned_by`, сортировка по цене, цветная маркировка + легенда. Смена модели пользователем сбрасывает слайдеры температуры/top_p к дефолтам.
- **Модель и настройки per-чат**: каждая вкладка запоминает свою модель (`chat.model`) и инкапсулированные настройки (`chat.settings`). При переключении вкладок дропдаун восстанавливает модель чата (без сброса параметров) и панель — настройки чата (`applyChatSettings`); изменения слайдеров/полей live-обновляют `chat.settings` активного чата и персистятся на сервере при отправке. При **создании нового чата** параметры сбрасываются к дефолту: модель `deepseek-v4-flash`, температура `1`, top_p `1`, «Лимит токенов» и «Стоп слова» очищены, стратегия — «Нет».
- Переключение вкладок сообщает серверу (`POST /api/sessions/{id}/activate`) — какая вкладка открыта (для восстановления активного чата).
- Первое сообщение нового чата становится системным промптом (сервер); в UI оно отображается обычным пузырём пользователя, а при восстановлении запись с ролью `system` рендерится как вопрос-сторона qa-блока.
- Вкладки чатов: несколько чатов в памяти страницы (без localStorage). `[+]` создаёт вкладку; первый вопрос переименовывает её. Переключение вкладок меняет отображаемый чат (состояние сохраняется). Всегда минимум одна вкладка.
- «Подвести итоги»: постоянный чат с фиксированным названием; модель получает TOON-контекст всех остальных чатов (в т.ч. метаданные ответов), follow-up работают.
- Раскладка: вкладки 20% | чат 60% | настройки 20%; на экранах <700px панели перестраиваются.
- Reasoning-модели: рассуждения скрыты под сворачиваемой меткой «Размышление» (`<details>`), свёрнуты по умолчанию, со спиннером во время размышления. Пока модель генерирует ответ, в баббле ассистента показывается **вейтер** (спиннер `.message__waiter`); по завершении (`done`) вейтер убирается и весь текст ответа появляется целиком. При появлении бабла-вейтера (отправка, `reasoning_start`, `reasoning_end`) окно чата **автоматически прокручивается вниз**.
- Настройки генерации (инкапсулированы per-чат). **Привязываемые** первым сообщением — блокируются для привязанного чата (`disabled`, значения видимы): модель, «Температура» (`temperature` 0–2), «top_p» (0.01–1 — ползунок не даёт выставить 0), «top_k» (число 1–100, пусто = по умолчанию), **«Стратегия контекста»** — радиокнопки (кастомные, доступны с клавиатуры) `Нет`/`Саммаризация`/`Sliding Window`/`Sticky Facts`/`Branching` (по умолчанию «Нет»). Числовой инпут показывается **только** для `Саммаризация`/`Sliding Window`/`Sticky Facts` (N: дефолты 5/10; K: дефолт 10), для `Нет`/`Branching` — скрыт. Подсказка под блоком — шаблон с **живым** значением поля (`{N}`/`{K}` подставляется при вводе). **Гибкие** — меняются на лету: «Лимит токенов» (`max_tokens`), «Стоп слова» (`stop` через запятую), «Режим ответа». Все отправляются с каждым запросом; привязываемые сервер фиксирует первым сообщением.
- **Панель фактов** (стратегия `facts`): показывается, как только у активного чата выбрана/зафиксирована `facts` (в т.ч. в новом чате до первого сообщения); для остальных стратегий, чата «Итоги» и ephemeral — скрыта. Колонка чата делится на две части — слева чат, справа панель фактов (только чтение): пары **«ключ: значение»** (ключ приглушённым цветом), легаси-строки — как есть. Перегородка `.chat__splitter` тянется мышью (минимальные ширины, ширина в `localStorage`); список обновляется по SSE-событию `facts` и при восстановлении; на экранах <700px панель перестраивается под чат.
- **Вид «Память»** (вкладка в полосе видов, только для обычных чатов): сверху — горизонтально прокручиваемая строка вкладок памяти; в конце строки — поле названия новой вкладки, объёмная кнопка-иконка БД (нажата = сохранять в БД) и `[+]`. Новые вкладки появляются **слева** от блока создания и активируются, кнопка БД после создания **сбрасывается**; у вкладки есть × для удаления, а у персистентной — **иконка БД перед названием** (та же, что на кнопке). Внутри активной вкладки — форма «ключ»/«значение»/«Сохранить» (сохранение очищает поля и добавляет строку «ключ: значение» со ссылкой «удалить» справа; удаление строки также удаляет запись из БД у персистентных вкладок). Любое изменение синхронизируется на сервер (`PUT …/memory`). После перезагрузки клиента восстанавливаются только персистентные вкладки; флаг персистентности фиксируется при создании вкладки. Все непустые пары из всех вкладок чата подставляются в запросы к LLM (§3.10).
- **Вид «Профиль»** (кнопка-вид в полосе видов с иконкой-человечком, прижата к правому краю; доступна всегда): набор вкладок-профилей, создаваемых полем названия и `[+]` (вкладки всегда персистентны — кнопки БД нет). Внутри активной вкладки — пять обязательных полей с подсказками («Как ко мне обращаться», «Стиль общения», «Язык диалога», «Формат ответа», «Ограничение ответа») и кнопки **«Сохранить»** (сохраняет/перезаписывает профиль) и **«Установить текущим»** (сохраняет и делает активным; у активной вкладки показывается зелёная галочка, у остальных снимается). Удаление вкладки удаляет профиль. Любое изменение синхронизируется на сервер (`PUT /api/profiles`). Профиль не привязан к чату — активный общий для всех чатов (§3.11).
- **Блокировка без профиля**: если активного профиля нет, отправка в обычном чате не уходит в LLM — в чате показывается блок «Необходимо создать и установить профиль.» (кнопка «Открыть профиль» переключает на вид «Профиль»). Сервер дублирует проверку (`code: profile_required`). Данные активного профиля подставляются в системный промпт.
- **Ветвление** (стратегия `branching`): у привязанного чата рядом с полем ввода — кнопка-**иконка** git-branch (та же, что на вкладках; `title`/`aria-label` «Продолжить в другом чате», по высоте равна кнопке «Отправить» за счёт flex-растягивания, заблокирована на время стрима). По клику `POST /api/sessions/{id}/branch` создаётся чат-снапшот, открывается новой активной вкладкой с иконкой перед названием (название дублирует родительское и сохраняется при восстановлении). Ветвиться можно многократно (цепочки); удаление родителя потомка не ломает.
- **Инфоблок чата** (`.chat-info`, фиксированная полоска внизу колонки чата во всю ширину): `модель · temperature N · top_p N · top_k N · токенов: N — макс. контекст · контекст: P% · Общая стоимость: $C`. Токены — сумма `prompt+completion` по метаданным истории этого чата; контекст — из `context` модели в `GET /api/models` (формат десятичный: `262K`/`1M`, неизвестная — «—»); **`контекст: P%`** — использование окна последним запросом (`prompt_tokens` последнего ответа / лимит): приглушён <80%, жёлтый ≥80%, красный ≥95%; **Общая стоимость** — сумма `cost_usd` по ответам чата (при отсутствии данных — «—»). Для непривязанного чата показывается текущий выбор (что привяжется). Если содержимое не вмещается в одну строку, блок переносится максимум на две (`-webkit-line-clamp: 2`).
- «Режим ответа» (тумблер): выкл — JSON-режим: `response_format={"type":"json_object"}` + системный промпт «Выдавай ответ строго в формате JSON.» (передаётся как `system_prompt` запроса). Рендер JSON-конверта `{thinking, response, date, tokens}`.
- **«Сожжено токенов: N»** (внизу блока параметров) — сумма `prompt+completion` токенов всех запросов к LLM по всем чатам, включая саммаризационные (из событий `request_log`). Персистентный: после перезагрузки страницы/рестарта сервера показывает накопленную сумму по живым чатам (удаление чата счётчик не уменьшает).
- **График токенов по сообщениям** (`.chartbar` внизу окна, Chart.js): столбчатая диаграмма. По оси X — сообщения пользователя по порядку (ширина столбика 1: первый запрос — прямоугольник X 0–1), по Y — расход токенов за сообщение. **Сворачивание**: клик по chevron/строке заголовка скрывает область диаграммы (заголовок остаётся); по умолчанию **свёрнут**, состояние в `localStorage` (ключ `pomogator2k:chart-collapsed`, переживает F5). **Тумблер «цветной режим»** (перед легендой, по умолчанию выключен; в `localStorage`):
  - **выкл** — один столбик на сообщение = **всего токенов** (вход+выход+саммаризация+факты), тултип «Сообщение №N · всего: T ток.»; легенда скрыта;
  - **вкл** — стек снизу вверх: **вход** (синий — `prompt_tokens` основного запроса), **выход** (зелёный — `completion_tokens` основного, т.е. ответ + рассуждения), **саммаризация** (янтарный — все токены служебного запроса; прикрепляется к следующему основному), **факты** (фиолетовый — все токены запроса экстрактора; прикрепляется к текущему ходу). Тултип: «Сообщение №N», «вход: X ток.», «выход: Y ток. (рассуждение: R)», «саммаризация: Z ток. (…)», «факты: F ток. (…)» и «всего: T ток.».

  Горизонтальный пунктир — лимит контекста модели (относится к входной части, т.е. к верхней границе синего сегмента); если лимит выше данных — пунктир у верхней кромки с пометкой «выше». Показывает **активный чат**, обновляется при переключении вкладок и поступлении `request_log`. Данные — `requests` из состояния сессии (восстанавливаются после F5 и рестарта). Если Chart.js не загрузился (нет CDN), в области графика показывается надпись «График недоступен (нет Chart.js)»; при пустой истории область остаётся пустой (без подписи).
- Блок «вопрос + ответ»: пара «пользователь → ассистент» в `.qa`; строка статистики `.qa__stats`: `время, вход, выход, рассужд., цена` (из серверного `meta`; прочерк при отсутствии).
- Приветственное сообщение «Привет! Чем могу помочь?» при создании чата.
- Отправка: кнопка или `Enter`; `Shift+Enter` — перенос; кнопка блокируется в занятом чате (`chat.busy`). В каждом чате — не более одного запроса; стрим продолжается в фоне при переключении вкладок.
- Поле ввода: авторесайз, максимум 2 строки; при превышении — вертикальный скролл.
- Ошибки — в bubble «Ошибка: …»; пустой ответ — «(пустой ответ)»; при `finish_reason=length` — «<LLM уперлась в ограничение по токенам: N>». При **лимите контекста** (`code=context_length_exceeded`) — спец-блок `.message--context-limit` (янтарный, ⚠) с локализованным сообщением и кнопками **«Новый чат»** и **«Подвести итоги»** (чтобы чат не оставался заблокированным).

### 5.4. Команды и автокомплит

- При вводе «/» в поле ввода над ним показывается дропдаун команд (фильтрация по префиксу; на текущий момент одна команда).
- `Tab`/`Enter`/клик по пункту — вставка команды **в начало строки** поля ввода + пробел. `↑`/`↓` — навигация, `Esc` — закрыть.
- Список команд: `COMMANDS` в `app.js`.

### 5.5. Команда `/optimize-prompt`

- Ввод `{content}` в виде `/optimize-prompt USER_TEXT` при отправке создаёт **изолированный временный чат** (`kind=ephemeral`):
  - модель — выбранная в текущем чате;
  - настройки — `temperature: 0.1`, `top_p: 0.01`;
  - системный промпт — «Действуй как профессиональный промт-инженер. Создай детальный промт для языковой модели по запросу: USER_TEXT. Промпт должен быть на языке запроса, лаконичен и структурирован.» (USER_TEXT — текст после команды);
  - пользовательское сообщение в изолированном чате — `USER_TEXT`.
- Результат выводится в **модальном окне**: стрим ответа, строка статистики, кнопка «Копировать» (буфер обмена) и «Закрыть». Закрытие также по клику вне окна и по `Esc`.
- При закрытии модального окна временная сессия удаляется и с сервера (`DELETE /api/sessions/{id}`), и из клиента. Незавершённый стрим прерывается (`AbortController`).
- Если после команды нет текста — локальная подсказка без обращения к API. Исходный чат при этом не изменяется.

### 5.6. Консольное логирование

Браузер логирует в консоль (DevTools) весь обмен с сервером:

- `[клиент→сервер] …` — исходящие запросы (POST/DELETE, тела);
- `[клиент←сервер] …` — входящие события (SSE-чанки, статусы).

Управляется флагом `CLIENT_LOG_ENABLED` в начале `app.js`.

- Статика раздаётся через FastAPI StaticFiles (без path traversal).
- Валидация тел запросов — pydantic; лимит длины `content` ≥ 1.
